# iCloud sync and backups

Charge Ledger uses SwiftData with the user's **private CloudKit database**. There is no app login or custom server. Recording and reporting work from the local store while offline. Apple schedules transfers; **Check iCloud status** checks the account and does not force a completed sync.

## Configure the signed app

1. Open `ChargeLedger/ChargeLedger.xcodeproj` in Xcode 16 or later. Select the app target and your Apple Developer Program team in **Signing & Capabilities**. CloudKit requires a team with the iCloud capability.
2. Keep the bundle identifier used for your installed app when upgrading an existing journal. Changing it creates a different app sandbox, so the old on-device store will not appear automatically. Export a JSON backup before moving to a different bundle identifier.
3. Under **iCloud**, enable **CloudKit** and create/select a container belonging to your team. The build setting **CHARGE_LEDGER_ICLOUD_CONTAINER** defaults to `iCloud.$(PRODUCT_BUNDLE_IDENTIFIER)`. Set it to the exact container identifier selected in Xcode if different. The same setting populates both the entitlement and the runtime container identifier; do not configure different values.
4. Confirm **Push Notifications** and **Background Modes → Remote notifications** are enabled. They are included in the checked-in project and regenerated by `Tools/create_project.py`. Automatic signing supplies the appropriate push entitlement for distribution. Silent CloudKit notifications do not require the user-facing monthly reminder permission.
5. Sign in to the same iCloud account on your test devices and allow iCloud access for the app. Build and run a development-signed version. CloudKit/Core Data creates the development schema when the store sets up and exports records. Check **Settings → iCloud sync**, then verify records on a second device.
6. Before TestFlight/App Store distribution, deploy the initialized **development schema to production** in CloudKit Console. Development and production databases are separate. Verify a production-signed build before shipping; never reset a production container to resolve a development issue.

For a simulator/local-only build without iCloud signing, remove the iCloud/push entitlements from that build configuration and remove `CloudKitContainerIdentifier` from its Info.plist (or set **CHARGE_LEDGER_ICLOUD_CONTAINER** to an empty string). The app then explicitly uses local storage at the same default URL. Do not change the container or bundle identity after shipping without a migration plan.

## What syncs

- Meter readings, 100% cycles, Trip A/B distances, actual Trip B counter readings and calculation references, individual saved prices, home-data completion status/timestamps, outside charging sessions, brands and locations.
- Reports are recalculated from those records on each device.
- Changes and deletions propagate. Sync is eventually consistent and can be delayed by connectivity, iCloud quota, account access, and iOS background scheduling.
- Meter defaults and monthly notification preferences stay on each device. JSON backups include meter defaults, with an explicit option to restore them. Reminder permission and scheduling are not restored or synced.

The current schema removes local unique constraints, adds required CloudKit defaults and tracks edit revisions. Logical UUIDs are preserved. Queries suppress duplicate UUIDs within each entity; reconciliation keeps the newest edit, with a persisted tie breaker, if restoring on two offline devices creates duplicate CloudKit rows. A monthly record and its meter checkpoint deliberately retain the same UUID across two different entities. Normal remote record edits and deletions use Apple's CloudKit merge behavior; simultaneous changes on different devices should be checked after both transfers finish.

## Upgrade and data preservation

The versioned migration includes the last local-only schema. Before changing that store, it writes a JSON safety copy to `Library/Application Support/ChargeLedger/Backups/before-icloud-upgrade.json`. The original default store name/location and logical IDs are retained. The schema upgrade opens locally first; that temporary container is released before reopening the same store with CloudKit, so the incompatible legacy constraints are never opened with mirroring. Migration failure shows an error and never replaces the journal with an empty store. An existing safety copy is retained on retry; Settings can export it after a successful launch, and the storage-error screen offers a share action when it exists.

The native migration test constructs an unversioned pre-iCloud store and checks all three entity types after upgrade. This test and a real installed-app upgrade **must still be run in Xcode**; the Linux development environment cannot validate SwiftData migration or live CloudKit transfers. Older historical schema variants should also be checked against an actual retained store before updating those installations.

The cycle-context update uses schema version 3, with the first CloudKit schema frozen as version 2 in `CloudJournalSchemaV2.swift`. The version 1 → 2 stage retains the original pre-iCloud safety copy; version 2 → 3 adds nullable `tripBCounterText`, `tripBPreviousCounterText` and `tripBPreviousCheckpointID` attributes. Existing normalized Trip B distances are preserved without fabricating raw counters. A new native test covers upgrading a version 2 store while retaining IDs, price/link data, revision metadata and unknown raw counters. Deploy the additional CloudKit fields from development to production before distributing this update. Native migration and signed live sync still require Xcode/device verification.

## Export/import through Files, including OneDrive

Choose **Settings → Your data → Export backup**. Save the JSON file to iCloud Drive, OneDrive, or another Files provider. To use OneDrive, install/sign in to its iOS app and enable its location in Files. These are manual backup copies; OneDrive is not a second automatic synchronization engine. No Microsoft API credentials or SDK are required.

**Import backup** reads and validates a Charge Ledger JSON backup, then previews new entries, newer matching edits and matches that will be kept. Confirm **Import backup** to merge. Matching UUIDs retain the newest edit; unrelated current entries remain. The plan is recomputed at confirmation in case iCloud delivered new data. Conflicting meter chronology or duplicate monthly identities reject the import before changes. All imported journal changes save together, with rollback on save failure. A pre-import copy is available through **Export pre-import safety copy**.

Import is a merge, not a replacement or an undo of newer edits. A backup from before an entry was deleted can restore that missing entry. To recover the exact snapshot independently of an existing journal, restore it into an empty installation. Avoid importing on a second device while its first iCloud download is still pending.

Version 2 JSON preserves raw decimal text, optional versus zero mileage, record IDs/links, dates, meter formats, per-record prices, legacy partial Trip B values, actual Trip B counters and calculation references, pending/entered/unchanged home metadata, brands and locations. Version 1 backups remain importable with actual counters unknown. Inconsistent counter arithmetic is rejected before import. Older app releases cannot import version 2 files; update the app before restoring them. Dates use Foundation JSON's seconds since 2001-01-01 UTC, retaining subsecond precision. Import accepts files up to 20 MB. CSV remains available for spreadsheet analysis and is not an import format; the three new counter columns are appended without moving the existing brand column.

Keep independent backup files: deleting a record on one synced device will also delete it from iCloud and other devices. Local safety copies live in the app sandbox and disappear if the app is uninstalled unless exported first.
